# dohan_core 파이프라인 — 후속 작업

계획 1(`2026-09-21-dohan-core-pipeline.md`) 실행 중 나왔지만 그 계획 안에서 처리하지 않은 항목들이다. 계획 2(Flutter 색칠 엔진)를 시작하기 전에 이 문서를 먼저 읽을 것.

실행 결과: 11개 태스크 + 최종 전체 리뷰 + 픽스 웨이브 1회, 26커밋.
`dohan_core` 63 테스트 / `dohan_cli` 12 테스트 / `dohan_gen` 5 테스트, `dart analyze` 클린.

## 1. 가장 먼저 할 일 — 실제 선화로 임계값 재측정

**지금 코드의 임계값은 전부 추측이고, 합성 픽스처가 통과할 때까지 모양을 바꿔가며 맞춘 것이다.** 최종 리뷰가 이 점을 지적했고, `tools/dohan_cli/test/cli_test.dart`의 픽스처 주석이 그 과정을 스스로 기록하고 있다.

실제 선화 10장을 돌려 다음 세 값을 정한다. 픽스 웨이브에서 CLI 표면을 열어뒀으므로 이제 가능하다.

```bash
cd tools/dohan_cli
dart run bin/dohan.dart build <선화.png> <출력디렉터리> \
    --min-tap-diameter=72 --min-region-area=24 --close-radius=3
```

거부되든 통과하든 측정값(영역 수 · 배경 비율 · 최소 영역 지름)이 출력되므로, 10장을 쓸어 담으면 캘리브레이션 표가 나온다.

**시작하기 전에 5줄짜리 선행 작업이 하나 있다.** `_requireInt` 옆에 `_requirePositiveInt`를 만들어 `--min-tap-diameter`와 `--min-region-area`에 쓴다. 지금은 음수·0을 조용히 받아 해당 게이트를 무력화하므로, 오타 난 음수가 "통과"로 보인다 — 캘리브레이션 표를 오염시킬 수 있는 유일한 함정이다.

### 특히 확인할 것

- **`minTapDiameterPx: 72`가 공룡 발톱에서 살아남는가.** 스모크 테스트가 77px로 통과했다 — 여유가 5px뿐이다. 계획서 상단에 적어둔 대로 원래 스펙의 64dp(≈193px)는 UI 버튼 기준을 도안 영역에 잘못 적용한 것이라 24dp(72px)로 낮춘 값이고, 이 역시 실측 근거가 없다.
- **`minRegionArea: 24`가 사진 입력에서 파편을 충분히 걷어내는가.** 종이 질감이 들어오면 파편이 수천 개 생긴다.
- **`closeRadius` 자동 추정이 실제 선 두께에서 맞는가.**

## 2. 계획 2가 시작 전에 해결해야 하는 것

### 2.1 `_fitToCanvas`와 `_inkToImage`가 `dohan_core` 밖에 있다

`tools/dohan_cli/bin/dohan.dart`의 private 함수다. 스펙 6장의 제목은 "파이프라인 — 한 벌만 구현한다"이고 8장은 앱이 `dohan_core`를 그대로 호출한다고 적혀 있는데, 현재 구조대로면 **계획 2가 이 둘을 재구현해야 한다.** 그리고 재구현이 어긋나면 정확히 누수가 되살아나는 지점이다 — 계획 1 안에서 이미 한 번 일어났다(아래 2.2).

둘 다 `dart:ui`를 건드리지 않으므로 `dohan_core`로 옮기는 데 장애물이 없다. 계획 2의 첫 태스크로 옮길 것.

### 2.2 `dohan_core`가 `dart:io`를 공개 배럴로 내보낸다

`lib/src/dohan_package.dart`가 `dart:io`를 import하고 배럴이 그것을 export한다. `readDohanPackage(Directory)`는 안드로이드에서 Flutter 에셋으로 실린 내장 도안을 읽을 수 없다 — 에셋은 `File`이 아니다.

`DohanMeta.fromJson`과 `decodeIndexMapPng`이 공개되어 있어 앱이 바이트 로더를 조립할 수는 있다. 다만 `dohan_core/io.dart`로 분리하고 `DohanPackage.fromBytes`를 추가하는 편이 낫다.

### 2.3 터치 지름이 스펙과 다르게 하드 리젝트다

스펙 6.2절은 "**경고 후 병합**"이라고 적었는데 구현은 `issues`에 넣어 도안을 통째로 거부한다. 계획서의 Global Constraints도 리젝트 규칙을 세 개만 나열했다. 발톱 하나 때문에 도안 전체가 죽는다. 캘리브레이션(1번) 결과를 보고 "작은 영역은 이웃에 병합"으로 되돌릴지 정할 것.

### 2.4 `--canvas-size`가 절대 임계값을 스케일하지 않는다

`minRegionArea: 24`, `minTapDiameterPx: 72`, `binarizeWindow: 31`은 1024 캔버스 기준의 절대 픽셀 수다. `--canvas-size=256`을 주면 디테일 기준이 조용히 4배 엄격해진다. 스펙 5.3절은 인덱스맵을 1024 고정으로 못박았으므로, 캔버스 크기를 바꿀 수 있게 두려면 세 값을 함께 스케일하거나 1024 외의 값을 막아야 한다.

## 3. 스펙 자체의 수정 필요 항목

계획 1 실행 중 스펙의 오류로 판명된 것들. 스펙 문서(`docs/superpowers/specs/2026-09-21-kkumul-coloring-app-design.md`)를 고칠 때 반영할 것.

| 스펙 위치 | 문제 | 처리 |
|---|---|---|
| 6.2절 배경 비율 | "배경 < 60% → 리젝트, 선이 새는 신호" — **방향이 반대다.** 누수가 나면 내부가 바깥과 이어져 통째로 BACKGROUND가 되므로 배경은 오히려 커진다. 지면을 꽉 채운 정상 도안(배경 2.3%, 6영역, 최소 지름 159px)을 거부했다 | 코드에서 제거 완료. **스펙 본문도 고칠 것** |
| 6.2절 터치 타겟 | "내접원 지름 < 64dp" — UI 버튼 기준을 도안 영역에 적용. 1024 캔버스에서 64dp ≈ 193px이라 정상 디테일이 전부 병합된다 | 72px(≈24dp)로 조정 완료, 실측으로 확정할 것 |
| 5.2절 `regionCentroids` | 무게중심은 고리·초승달에서 자기 영역 밖에 떨어진다. 동심원 4개가 전부 같은 좌표를 냈다 | `regionAnchors`(내접원 최대 지점)로 교체 완료. **스펙의 필드명·예시도 고칠 것** |
| 6.1절 2단계 | 리샘플 순서가 스펙 표와 구현이 반대(구현은 리샘플→이진화). 구현 쪽이 맞다 | 스펙에 편차로 명시할 것 |
| 15장 | 누수 회귀 테스트가 요구한 `BACKGROUND` 비율 단언이 없고, 게이트 경계(영역 3/4/120/121)가 미검증 | 테스트 보강 필요 |

**누수 판정은 현재 `tooFewRegions` 하나가 맡는다.** 배경 비율 규칙을 제거하면서 대체 검사를 넣지 않았다 — 최대 비율 검사는 값이 없다고 판단했다(전면 누수는 이미 영역 수 0으로 잡히고, 부분 누수는 최대 비율도 못 잡는다). 제대로 된 후속은 **봉쇄 검사**다: 잉크 바운딩 박스 안에서 배경이 차지하는 비율. 그림 자신의 경계 안쪽까지 배경이 파고들면 그것이 진짜 누수의 신호이고, 전역 비율과 달리 방향이 맞다. 캘리브레이션 데이터가 나온 뒤 설계할 것.

## 4. 이월한 minor 항목

최종 리뷰가 "나중에 해도 됨"으로 분류한 것들. 해당 파일을 건드릴 때 같이 처리하면 된다.

**성능·정확성에 영향 없음**
- `encodeRegionId`의 범위 검사가 `assert`뿐 (`labelRegions`가 `kMaxRegionId`에서 던지므로 파이프라인 경로로는 도달 불가)
- `PipelineOptions.closeRadius == 0` 분기가 `closeLines`의 no-op와 중복
- `decodeIndexMapPng`이 전체를 채운 뒤 모든 셀을 덮어씀
- `fillableRegionCount`가 `fillableRegionIds`를 다시 호출 (단일 O(N) 패스)
- `_smallestInscribedDiameter`가 영역 수로 이미 리젝트될 때도 전체 BFS

**문서가 틀린 것 (코드는 맞음)**
- `binarize` 주석이 창 크기를 `window`×`window`라 하나 실제는 `2*(window~/2)+1`
- `closeLines` 주석에 `.clamp(1, 8)` 언급 없음
- `pipeline.dart`의 `closeRadius` 주석이 "0은 테스트용"이라 하나 이제 실제 CLI 플래그다
- `cleanupRegions`의 4패스 캡 주석이 실제 종료 이유와 다름

**테스트 공백**
- 3단 이상 연쇄 병합, "선으로만 둘러싸인 파편" 폴백 경로
- `koreanSummary()`의 통과 분기가 실행은 되나 단언되지 않음
- 1024² 인덱스맵 왕복 테스트가 width/height를 단언하지 않음
- `_fitToCanvas`의 세로 레터박싱(`dstY`)이 미검증 — 가로만 덮임

**기타**
- `readDohanPackage`가 `e.message`만 감싸 `osError`를 잃음 (파일 없음 vs 권한 없음 구분 불가)
- `_boxImage` 테스트 헬퍼가 두 패키지에 중복됐고 이미 발산함 (core 쪽만 `gapWidth` 지원)
- `--difficulty`가 범위 검증 없음
- `generate.py`의 `provider` 바인딩이 `choices` 덕분에만 전수적 — provider 추가 시 `UnboundLocalError`
- `providers.py`와 `generate.py`에 테스트 없음

## 5. 계획 1에서 배운 것

리뷰가 찾아낸 결함은 **거의 전부 계획서가 제공한 코드 자체의 버그**였다. 구현자들의 전사는 매번 정확했다. 계획을 촘촘히 쓰면 계획의 오류가 그대로 코드가 되므로, 검증 단계가 유일한 방어선이 된다.

특히 값을 한 것:

- **실제로 실행해 보는 것.** 최종 리뷰가 찾은 Critical 2건(`cleanupRegions` 성능, 지면 꽉 찬 도안 거부)과 Important 1건(preview 왕복이 빈 페이지)은 전부 코드를 돌려서 나왔다. 읽기만 해서는 나오지 않았다.
- **합성 픽스처를 의심하는 것.** 통과할 때까지 모양을 바꾼 픽스처는 임계값을 검증하지 못한다. 픽스처가 게이트에 걸렸을 때 단언을 약화시키지 않고 멈춘 판단이 스펙 결함 하나를 드러냈다.
- **리포트 수치를 직접 대조하는 것.** 구현자 리포트의 테스트 개수 서술이 세 번 틀렸다(코드는 매번 정확했다). "방금 실행한 출력에서 그대로 인용하라"고 지시한 뒤로 사라졌다.
