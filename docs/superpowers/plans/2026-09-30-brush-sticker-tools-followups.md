## 1. 계획 5 가 시작하자마자 터뜨릴 것 — 가장 먼저 읽을 것

### 1.1 `ageMode` 를 런타임에 유아로 바꾸면 아이가 갇힌다

최종 리뷰가 프로브로 실증했다. 아동 모드에서 **지우개를 고른 상태**로 `ageMode` 를
`toddler` 로 바꾸면:

- 도구 줄 0개 (유아는 도구 줄을 숨긴다)
- 팔레트 0개 (`_buildContext` 가 지우개일 때 빈 상자를 준다)
- 캔버스를 탭해도 `fills = 0` (도구가 여전히 지우개인데 바꿀 수단이 사라졌다)

**아이가 아무것도 할 수 없는 화면에 갇힌다.** 계획 3 에는 `ageMode` 를 바꾸는 UI 가 없어
지금은 도달 불가지만, **계획 5 가 `내 정보` 화면을 붙이는 순간 이것이 첫 버그가 된다.**

고치는 법: `ageMode` 를 평범한 필드가 아니라 세터로 만들고, 유아가 되면 도구를 되돌린다.

```dart
  AgeMode get ageMode => _ageMode;
  set ageMode(AgeMode next) {
    _ageMode = next;
    // 유아는 도구 줄이 없다. 아동 모드에서 고른 도구를 그대로 들고 넘어가면
    // 바꿀 수단 없이 그 도구에 갇힌다.
    if (next == AgeMode.toddler) _tool = ToolKind.bucket;
    notifyListeners();
  }
```

**계획 5 의 디스패치에 이 항목을 직접 실을 것.**

### 1.2 스티커 두 손가락 — 크기 조절이 없고, 대신 순간이동한다

스펙 §5.5 와 §7.4 는 두 손가락으로 스티커 크기를 바꾸라고 하는데 **제스처가 없다.**
데이터 모델(`scale`, 클램프 [0.5, 2.0])은 준비돼 있다. 그 상태로 두 손가락을 올리면
`onPanUpdate` 가 두 포인터의 **중점**을 받아 스티커가 엉뚱한 자리로 **순간이동한다**
(실측: scale 1.0 그대로, x 32 → 41.3).

계획 3 에서 고치지 않은 이유: 둘은 **같은 수정**을 공유한다. 제대로 하려면 캔버스의
제스처를 `onPanStart/Update/End` 에서 `onScaleStart/Update/End` 로 옮겨야 하는데, 그것은
탭·팬·스케일의 상호작용을 전부 다시 짜는 일이고 마무리 픽스 웨이브에 넣기엔 회귀 위험이
크다. 순간이동은 데이터 손실이 아니라 아이가 다시 끌어 되돌릴 수 있는 상태다.

**함께 처리할 것** (아래 1.3 도 같은 작업에 딸려 온다).

### 1.3 `cancelStickerDrag` 가 없다

지금은 안전하다 — `DragGestureRecognizer` 가 일단 제스처를 받아들이면 취소 시에도
`onPanEnd` 를 부르므로 커밋되지 않은 이동이 남지 않는다. **다만 1.2 에서 `onScale*` 로
옮기는 순간 이 보장이 사라진다.** 그때 `cancelStickerDrag` 를 만들어
`_dragBefore` 를 되돌리고 버릴 것.

### 1.4 스티커 에셋 하나가 없으면 캔버스가 영영 안 그려진다

`coloring_screen.dart` 의 `_prepare()` 가 **전부 아니면 전무**다. 스티커 PNG 10장을
`rootBundle.load` 로 읽는데, 하나라도 없으면 거기서 던져서 `_shader`·`_regionsImage`
설정이 통째로 건너뛰어진다 → **캔버스가 영영 로딩 상태로 남는다.**

스티커 로딩을 `try` 로 감싸거나 셰이더 준비와 분리할 것. 계획 5 가 스티커를 늘리거나
원격 배포를 붙이면 바로 도달 가능해진다.

## 3. 그 파일을 다음에 열 때 같이 치울 것

### 3.1 `ColoringPainter.brushRevision` 은 죽은 인자다 — 그런데 위험하다

`paint` 도 `shouldRepaint` 도 읽지 않는다(`shouldRepaint` 는 무조건 `true`). 화면과
테스트가 계속 넘긴다.

**단순한 죽은 코드가 아니다.** 이름이 "다시 그리기 트리거"처럼 읽혀서, 나중에 누가
성능을 "최적화"하려고 이걸로 `shouldRepaint` 를 다시 짜면 **`cb9c60e` 가 고친 바로 그
버그가 돌아온다** — 아이가 손가락을 끄는 동안 화면에 아무것도 안 나타나고 손을 뗄 때
획이 통째로 튀어나오는 것. 라이브 스트로크는 `revision` 을 올리지 않기 때문이다.

지우거나, **왜 남겼고 왜 이걸로 `shouldRepaint` 를 짜면 안 되는지** 주석으로 못 박을 것.

### 3.2 중복 세 벌

- **PNG 디코더 두 벌**: `coloring_controller.dart` 의 `_decodePng` 와
  `coloring_screen.dart` 의 `_decodeBytes` 가 글자만 다른 같은 함수다.
  (계획서 Task 15 가 "이름이 다르면 있는 것을 쓸 것"이라고 적어 뒀는데 둘이 남았다.)
- **스티커 PNG 두 경로**: 화면이 `rootBundle` 로 10장을 디코드하고, `sticker_drawer.dart`
  가 같은 10장을 `Image.asset` 으로 또 읽는다. 메모리 두 벌(각 ≈2.6MB).
- **덮임 판정 술어 두 벌**: `BrushState.isEmpty` 와 `BrushPainter.paint` 첫 줄이 같은
  조건을 따로 적었다. `isEmpty` 는 테스트만 쓴다 — 한쪽을 고치면 다른 쪽이 조용히 어긋난다.

계획 1 에서 캔버스 맞춤 헬퍼 두 벌이 발산했던 사고와 같은 모양이다.

### 3.3 죽은 공개 API

`ColoringController.stickerAt` 을 `lib/` 와 `test/` 어디에서도 부르지 않는다.

## 5. 테스트 공백

최종 리뷰가 "대기"로 분류한 것들. 코드는 전부 프로브로 옳음이 확인됐고, 없는 것은
**회귀를 잡아 줄 그물**이다.

- `BrushState.base`(이전 세션에서 구운 이미지)를 non-null 로 태우는 테스트가 없다.
- 크레용의 **겹칠수록 진해지는** 동작(반투명의 존재 이유)이 미검증. 프로브로는 확인:
  2겹 알파 249/255 vs 1겹 217/255.
- 자동 저장 베이커가 **`schedule()` 시점에 불리지 않는다**는 불변식에 테스트가 없다.
- `"채움 명령이 색을 바꾸고 되돌린다"` 가 이름과 달리 `undo()` 를 부르지 않는다
  (되돌리기는 다음 테스트가 덮으므로 실제 공백은 아니다).

## 6. 판단 항목 — 고쳐도 되고 안 고쳐도 된다

- **지우개가 채움 위에서 손을 뗄 때까지 반응이 없다.** 브러시 잉크 위에서는 즉시
  지워지는데(clear 스트로크가 실시간으로 그려지므로) 채움은 `endStroke` 에서야 벗겨진다.
  실시간으로 하려면 묶음 명령 구성이 복잡해진다. 다음 UX 손질에서 볼 것.
- **`ShadeButton` 아이콘 방향.** `Shade.light`(연하게) → 작은 해, `Shade.dark`(진하게) →
  큰 해. "진하기"로 읽으면 일관되지만 "밝기"로 읽으면 거꾸로다. 버튼 안의 **색 자체**가
  올바른 1차 신호라 실해는 작다.
- **`cloud-01.png` 이 구름보다 발바닥에 가깝고 프레임 아래로 치우쳤다.** 자리표시자이므로
  디자이너나 생성물이 덮어쓰면 끝난다.
- **스티커 `instanceId` 의 타임스탬프 접두사가 사실상 장식이다.** 단조 카운터만으로 이미
  유일성이 보장된다. 다만 카운터가 어떤 이유로 리셋되면 접두사가 실제 방어가 되므로
  **남겨 두는 편이 낫다.**

## 8. 계획 3 에서 배운 것

계획 1·2 의 교훈이 또 반복됐다. **계획 3 에서 발견된 결함 아홉 건이 전부 계획서가 제공한
코드 자체의 버그였고, 구현자의 전사는 매번 정확했다.** 더 나아가 **두 번은 구현자가 옳고
내 수정이 틀렸다.**

### 읽어서는 안 나오고 돌려야 나오는 것들

최악의 두 버그가 모든 태스크 리뷰를 통과한 뒤 최종 리뷰에서 **실행으로** 잡혔다.

- **`shouldRepaint` 가 긋는 중에 false 를 돌려줬다.** 라이브 스트로크는 `revision` 을
  올리지 않고 스티커 드래그는 목록 길이를 안 바꾼다. 아이가 손가락을 끄는 동안 화면에
  아무것도 안 나타났다. **테스트 173개가 전부 통과했다** — 전부 컨트롤러 **상태**만
  단언하고 렌더 결과를 보지 않았기 때문이다.
- **`loadStickers`/`loadBrushPng` 를 아무도 부르지 않았다.** 저장은 되고 되읽기가
  없었다. 아이의 스티커와 브러시가 디스크에 남은 채 화면에서 사라졌다.

교훈: **UI 를 만드는 계획은 "렌더 결과를 읽는 테스트"를 반드시 하나는 넣는다.**
상태 단언만으로는 화면이 멈춰 있어도 초록이다.

### 테스트가 자기 주제를 못 잡는 경우

최종 리뷰가 `UndoStack.push` 의 `removeFirst` 를 `removeLast` 로 뒤집었다 — 아이의
**가장 최근** 조작을 버리는 치명적 역전인데 **173개가 전부 통과했다.** 그 테스트는
개수만 보고 어느 쪽이 남았는지 보지 않았다.

같은 일이 태스크 3 에서도 있었다(길이 0 선분 가드 테스트가 가드를 지키지 못했다).
**교훈: 회귀 테스트를 추가할 때는 고치려는 코드를 일부러 되돌려 빨개지는지 확인한다.**
이 계획에서는 그것을 매 픽스 라운드에 요구했고, 매번 값을 했다.

### 구현자가 옳았던 두 번

- **Dart 의 `NaN.clamp(0,1)` 은 NaN 이 아니라 1.0 을 돌려준다**(`compareTo` 가 NaN 을
  가장 크게 정렬한다). 그래서 길이 0 선분 가드는 **어떤 테스트로도 존재를 구분할 수
  없다.** 내가 "실패하는 것을 증명하라"고 두 번 시켰는데 애초에 불가능한 요구였다.
- **극좌표에서 삼각파 반지름 보간은 날카로운 별을 만들 수 없다** — 기하적으로 곡선이다.
  내가 준 숫자를 아무리 바꿔도 꽃이었다. 구현자가 두 점 직선 극좌표 공식으로 바꿨다.

**교훈: "구현자가 틀렸을 것"이라는 기본 가정도 틀릴 수 있다. 보고된 관찰은 재현해 보고
판단할 것.**

### 오케스트레이션

- **구현자 대신 커밋하기 전에 살아 있는지 확인할 것.** 완료 알림을 "종료"로 오독하고
  아직 작업 중인 구현자의 스테이징을 먼저 커밋한 적이 있다. 구현자가 정확히 지적했다.
- **리뷰어와 다음 구현자를 같은 워킹 트리에서 동시에 돌리지 말거나, 리뷰어에게
  `git show <commit>:<path>` 로 읽게 할 것.** 한 번은 리뷰어가 스스로 오염을 알아채
  운이 좋았다.
- **`flutter test` 를 `grep` 에 파이프하지 말 것** (블록 버퍼링), **`printf` 로 커밋
  메시지를 만들지 말 것** (`%` 가 잘라먹는다), **`+N -M` 은 누적 집계이지 테스트
  번호가 아니다** (한 구현자가 오독해 없는 결함 세 개를 보고했다).
