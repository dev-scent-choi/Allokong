# 브러시 · 스티커 도구 설계 (계획 3)

**상위 스펙**: `docs/superpowers/specs/2026-09-21-kkumul-coloring-app-design.md`
이 문서는 그 스펙의 **7장(렌더링 엔진) · 9장(연령 분기) · 10장(화면 명세)** 을 계획 3 범위에서
구체화하고, 일부는 **의도적으로 다르게 정한다**. 다른 부분은 3절에 모아 근거와 함께 적었다.
충돌하면 계획 3 범위에서는 이 문서가 우선한다.

**전제**: 계획 2 완료 상태. 앱 63 테스트, 탭 후입 + 프래그먼트 셰이더 렌더링 + 되돌리기 +
자동 저장이 동작한다. 계획 2 후속 문서(`2026-09-25-coloring-engine-followups.md`)를 함께 읽을 것.

---

## 1. 범위

**만든다**: 크레용 · 붓 · 지우개 · 스티커 도구, 브러시 레이어 렌더링, 명령 스택 확장,
브러시·스티커 저장, `AgeMode` 와 `settings.json`, 명도 전환.

**만들지 않는다**:

| 항목 | 어디로 | 왜 |
|---|---|---|
| `내 정보` 화면 (연령 변경 UI) | 계획 5 | 탭 내비게이션이 아직 없다. 계획 3 은 `settings.json` 을 읽고 쓰는 계층까지만 만들고, 시험은 파일을 직접 고쳐서 한다 |
| `thumb.png` (갤러리 썸네일) | 계획 5 | 갤러리가 없다. 지금 만들면 아무도 읽지 않는다 |
| 스티커 회전 | 미정 | 포맷에 `rotation` 필드는 두되 항상 `0` 을 쓴다. 두 손가락으로 크기와 회전을 동시에 다루는 것은 6~9세에게 어렵고 대개 의도치 않게 비뚤어진다. 나중에 포맷을 안 바꾸고 제스처만 추가할 수 있다 |
| 브러시 굵기 선택 UI | 미정 | 상위 스펙 어디에도 없고, 크레용과 붓이 이미 굵기·질감이 다른 두 도구다 |

## 2. 정해진 것 요약

| 결정 | 값 |
|---|---|
| 브러시 렌더링 | 매 프레임 스트로크 목록 재생 (오프스크린 이미지 누적 안 함) |
| 브러시 마스킹 | 도안별 정적 마스크 + `BlendMode.dstIn` (셰이더 분기 아님) |
| 지우개 | 손가락 밑의 **맨 위** 것을 지운다. 구현은 `BlendMode.clear` 스트로크 |
| 명령 스택 | `ArtworkState` 하나를 받는 단일 스택. 레이어별로 쪼개지 않는다 |
| 아동 팔레트 | 8색 스와치 + 명도 순환 버튼 (24색을 다 펼치지 않는다) |
| 명도 버튼 위치 | 앱바. 누를 때마다 밝게 → 기본 → 어둡게 |
| 스티커 배치 | 서랍에서 누르면 캔버스 한가운데 출현 → 끌어서 이동 → 두 손가락으로 크기 |

## 3. 상위 스펙과 다르게 정한 것

### 3.1 브러시 마스킹을 셰이더가 아니라 정적 마스크로 (7.3절)

상위 스펙 7.3: *"브러시 레이어를 합성할 때 **셰이더가** 픽셀별로 `regionId >= 2` 인지 확인한다."*

**다르게 한다.** 칠할 수 있는 픽셀인지 아닌지는 **도안마다 고정**이므로 런타임에 픽셀마다
물을 이유가 없다. 도안을 읽을 때 `regions.png` 에서 마스크 이미지를 한 번 만들어두고,
브러시를 합성할 때 한 번 블렌드한다.

```
canvas.saveLayer(bounds, Paint());
  drawBase();          // 이전 세션에서 구운 brush.png (있으면)
  drawStrokes();       // 이번 세션 스트로크 전부
  canvas.drawImage(paintableMask, Offset.zero,
                   Paint()..blendMode = BlendMode.dstIn);
canvas.restore();
```

**결과는 스펙과 동일하다**: 선 위에도 배경에도 브러시가 남지 않고, 영역 경계는 자유롭게
넘나든다(7.3절이 의도한 관대함). 비용만 다르다 — 픽셀별 셰이더 분기 대신 정적 이미지 한 장과
블렌드 한 번이고, 계획 2 의 `fill.frag` 을 건드리지 않는다.

마스크는 도안당 1024² RGBA 한 장(4MB)이고 도안과 수명을 같이한다.

### 3.2 아동 팔레트를 24색 펼침이 아니라 8색 + 명도 전환으로 (9장)

상위 스펙 9장은 아동 팔레트를 **24색**(8색 × 3명도)으로, 10.3절은 터치 타겟을
**최소 64dp** 로 정한다. **이 둘은 휴대폰에서 동시에 성립하지 않는다.**

320dp 폭 기준 실측 산수:

- 한 줄에 64dp 스와치 5개 (320 ÷ 64 = 5)
- 24색 → 5줄 → 세로 320dp
- 본문 높이는 약 542dp (640 − 앱바 64 − 제스처 34)
- 팔레트가 본문의 **59%** 를 먹고, 캔버스가 222dp 로 팔레트보다 작아진다

가로 스크롤은 답이 아니다 — 계획 2 최종 리뷰가 잡은 결함이 정확히 그것이고(글을 못 읽는
아이는 줄이 스크롤된다는 것을 알아낼 수 없다), 스와치를 64dp 밑으로 줄이면 10.3 을 어긴다.

**그래서 8색 스와치는 그대로 두고 명도를 별개 축으로 뺀다.** 색은 24가지를 다 쓸 수 있고,
터치 타겟은 전부 64dp 를 지키며, 팔레트가 차지하는 세로는 2줄(128dp)로 끝난다.
스펙의 "8색 × 3명도" 라는 구조 자체가 이미 명도를 별개 축이라고 말하고 있다.

### 3.3 지우개를 "선택된 레이어"가 아니라 "맨 위 것"으로 (7.5절)

상위 스펙 7.5 첫 줄은 *"현재 선택된 레이어에서 지운다"* 인데, 6~9세에게 레이어를 고르게 하는
UI 는 없고 만들어서도 안 된다. 같은 절의 나머지 세 줄은 오히려 "손가락 밑에 있는 것을
지운다"로 읽힌다. **후자로 정한다.** 아이는 "지우개로 문지르면 지워진다"만 알면 된다.

## 4. 상태 구조와 되돌리기

### 4.1 한 상태, 한 스택

레이어마다 스택을 따로 두면 아이 경험이 깨진다. 칠하고 → 긋고 → 스티커를 붙인 뒤 되돌리기를
세 번 누르면 스티커 → 획 → 채움 순으로 돌아가야 하는데, 스택이 갈라지면 그 순서를 지킬 수 없다.

```dart
/// 한 작품의 편집 상태 전부. 모든 명령은 이것 하나를 받는다.
class ArtworkState {
  final FillState fills;        // 계획 2 의 것 그대로
  final BrushState brush;
  final StickerState stickers;
}

abstract class Command {
  void apply(ArtworkState state);
  void revert(ArtworkState state);
}
```

`Command.apply(FillState)` → `apply(ArtworkState)` 는 **호환성을 깨는 변경**이다.
`command.dart`, `command_test.dart`(5개), `coloring_controller.dart` 가 영향을 받는다.
계획 2 가 이 경계를 좁게 감싸 두어 범위는 작다.

### 4.2 명령 네 가지

| 명령 | 내용 | 비고 |
|---|---|---|
| `FillCommand` | `{regionId, before, after}` | 계획 2 의 것 그대로. `after == null` 이 "칠 지우기" |
| `StrokeCommand` | `{Stroke stroke}` | 획에는 바꿔칠 정체성이 없다 |
| `StickerCommand` | `{instanceId, before, after}` | `before == null` 추가, `after == null` 삭제, 둘 다 있으면 이동·크기 |
| `BatchCommand` | `List<Command>` | 아래 4.3 |

`FillCommand` 와 `StickerCommand` 가 `{id, 이전, 이후}` 로 같은 모양인 것은 의도된 대칭이다.

### 4.3 `BatchCommand` 가 왜 필요한가

지우개가 "맨 위 것"을 지우므로, **한 번 쓸어내리는 동안 명령이 여러 개 나온다** — 브러시
자국을 지우는 clear 스트로크 하나, 지나간 스티커 삭제 N 개, 벗겨진 채움 M 개. 아이는 되돌리기
한 번에 그 손짓 전체가 돌아오기를 기대한다. 묶지 않으면 되돌리기를 일곱 번 눌러야 한다.

`BatchCommand` 는 `apply` 를 순서대로, `revert` 를 **역순으로** 실행한다.

### 4.4 되돌리기 깊이

스택 깊이는 항상 50 이다(상위 스펙 7.6: *"내부 스택은 동일하다"*). 유아 모드는
`ColoringController` 가 **연속 되돌리기를 한 번으로 제한**한다 — 새로 무언가를 한 뒤에는
다시 한 번 가능하다.

## 5. 렌더링

### 5.1 레이어 순서 (상위 스펙 7.1 그대로)

```
5. 스티커     오브젝트를 순서대로 그린다. 선화보다 위
4. 선화       lineart.png, 알파 블렌드
3. 브러시     스트로크 재생 + dstIn 마스크 (3.1절)
2. 채움       fill.frag (계획 2 의 것, 수정 없음)
1. 흰 배경
```

### 5.2 브러시를 이미지에 누적하지 않는 이유

`ui.Image` 는 불변이다. 덧그리려면 "기존 이미지 + 새 선분"을 매번 다시 래스터화해 **새 이미지를
만들어야** 하고, 1024² 면 한 장에 4MB 다. 아이가 손가락을 끄는 동안 매 프레임 생긴다.
계획 2 후속 §3.1 의 팔레트 이미지 문제가 16배 크기로 돌아온다.

**매 프레임 스트로크 목록을 다시 그린다.** 획 50개 × 점 100개라도 선분 5천 개고 GPU 에게는
가벼운 일이다. 부수 효과가 좋다 — 상위 스펙 7.6 이 말하는 *"레이어를 지우고 남은 스트로크를
리플레이"* 가 **따로 필요 없다.** 목록에서 마지막 하나를 빼면 다음 프레임이 이미 그것이다.
`ui.Image` 는 저장할 때 딱 한 번 만든다.

### 5.3 자료 구조

```dart
enum BrushKind { crayon, brush, eraser }

class Stroke {
  final BrushKind kind;
  final Color color;          // eraser 는 무시
  final double width;
  final List<Offset> points;  // 캔버스 좌표
}

class BrushState {
  ui.Image? base;             // 이전 세션에서 구운 brush.png. 없으면 null
  final List<Stroke> strokes; // 이번 세션에 그은 것
}
```

`eraser` 스트로크는 `BlendMode.clear` 로 그린다. **지우개도 그냥 스트로크 하나로 쌓이므로**
재생 순서만 지키면 지운 자국까지 그대로 재현된다. 지우개를 "스트로크 삭제"로 구현하면
재생이 훨씬 복잡해진다.

### 5.4 지우개가 무엇을 지울지 고르는 법

픽셀을 읽지 않는다. 브러시 레이어는 우리가 직접 재생하므로, 어떤 점에 브러시 잉크가 있는지를
**스트로크 목록과의 거리 계산**으로 정확히 알 수 있다 — 각 스트로크의 각 선분에 대해 점까지의
거리가 `width / 2` 이하인가. 획 50개 × 점 100개면 한 번 판정에 5천 번 거리 계산이고, 탭 한
번에 그 정도는 문제가 되지 않는다.

한 번의 지우개 손짓은 이렇게 처리한다:

1. 시작점 아래에 스티커가 있으면(위에 있는 것부터) → `StickerCommand`(삭제) 하나. **끝낸다.**
   스티커를 떼려던 아이가 밑에 있는 그림까지 지우는 일은 없어야 한다.
2. 아니면 → `BlendMode.clear` 스트로크 하나(`StrokeCommand`)를 깐다. 그리고 지나간 각 점에서
   **살아 있는 스트로크가 그 점을 덮고 있지 않으면**, 그 점의 영역에서 채움을 벗긴다
   (`FillCommand`, `after == null`). 영역 하나당 한 번만.
3. 1~2 에서 나온 명령을 `BatchCommand` 로 묶어 한 번에 쌓는다.

**알려진 한계**: 앱을 다시 켜면 이전 세션의 브러시 잉크는 `base` 이미지 안에 있고 스트로크
목록에는 없다. 그래서 그 위를 지우면 채움까지 같이 벗겨진다. 실제로는 clear 스트로크가 그
잉크도 지우므로 아이 눈에는 둘 다 사라지는 것으로 보이고, 어색하지 않다. 정확히 하려면 `base`
픽셀을 읽어야 하는데 그 비용을 낼 값이 아니다.

### 5.5 스티커

상위 스펙 7.4 대로 래스터로 굽지 않고 오브젝트 목록으로 둔다.

```dart
class Sticker {
  final String instanceId;  // 이 배치 한 건의 id
  final String stickerId;   // 'star-01'
  final double x, y;        // 캔버스 좌표, 중심
  final double scale;
  final double rotation;    // 항상 0 (1절 참조)
}
```

서랍에서 누르면 캔버스 한가운데에 기본 크기로 나타난다. 놓는 동작이 실패할 수 없다는 것이
이 방식의 핵심이다 — 아이가 손을 어디서 떼든 스티커는 이미 화면에 있고, 마음에 안 들면 끌면
된다. 끌어서 이동, 두 손가락으로 크기.

## 6. 저장 포맷

상위 스펙 11장 구조 그대로.

```
artworks/<id>/
  artwork.json      { dohanId, fills, updatedAt }   ← 계획 2 그대로
  stickers.json     스티커 오브젝트 목록 (없으면 파일 없음)
  brush.png         구운 브러시 레이어 (없으면 파일 없음)
```

### 6.1 자동 저장 비용을 0 으로 유지한다

`brush.png` 를 만들려면 스트로크를 `ui.Image` 로 래스터화하고 PNG 로 인코딩해야 한다.
자동 저장은 1초 디바운스마다 돈다. 아이가 계속 그리는 동안 매초 1024² PNG 를 굽는 것은
감당이 안 된다 — 계획 2 에서 선화 PNG 왕복 하나가 화면 열 때마다 36ms 를 먹은 것을 잡았다.

`Autosave` 가 다 만들어진 값 대신 **굽는 함수를 함께 받아두고 실제로 쓸 때 한 번만 부른다.**

- 탭·획마다 드는 비용: **0**
- 디바운스가 끝났을 때만 한 번 굽는다
- 마지막 저장 이후 스트로크 목록이 바뀌지 않았으면 **굽지 않고** `brush.png` 를 건드리지 않는다

채움만 바꾸는 아이(유아 모드가 정확히 그렇다)는 브러시 인코딩 비용을 한 번도 내지 않는다.

### 6.2 파일 셋의 원자성

`rename` 은 파일 하나 안에서만 원자적이다. 셋을 연달아 rename 하다 앱이 죽으면 `artwork.json`
은 새것이고 `brush.png` 는 옛것인 상태가 남는다. 이것은 파일이 깨진 것이 아니라 **마지막 1초가
레이어마다 다르게 남은 것**이고, 아이 눈에는 "방금 그은 획 하나가 없다" 정도다. 폴더 단위 쓰기로
진짜 원자화할 수도 있지만 그 복잡도를 낼 값은 아니다.

대신 **읽을 때 세 파일을 독립적으로 취급한다.** `brush.png` 가 깨져 있어도 채움과 스티커는
살아난다 — 계획 2 의 `load()` 가 손상과 읽기 실패를 구분하는 것과 같은 원칙이고, 읽기 실패는
여전히 던진다(그래야 자동 저장이 멀쩡한 파일을 덮지 않는다).

## 7. 화면과 도구 UI

### 7.1 세로 예산 (320 × 640 기준)

| | 높이 |
|---|---|
| 앱바 (제목 · 명도 순환 버튼 · 되돌리기) | 64 |
| **캔버스** | **350** |
| 도구 줄 (64dp × 5, 320dp 폭에 정확히 다섯) | 64 |
| 상황별 영역 | 128 |
| 제스처 영역 (`SafeArea`) | 34 |

**상황별 영역의 높이는 고정한다.** 도구를 바꿀 때마다 높이가 변하면 캔버스가 늘었다 줄었다
하면서 아이가 그리던 그림이 화면에서 튄다. 최대 높이를 잡아두고 안에 든 것만 바꾼다.

| 선택한 도구 | 상황별 영역 |
|---|---|
| 양동이 · 크레용 · 붓 | 8색 스와치 (2줄) |
| 지우개 | 비움 |
| 스티커 | 스티커 서랍 (2줄 × 5 = 10개) |

1단계 스티커는 10개로 한다 — 서랍이 두 줄에 들어가는 수다. 더 넣으면 스크롤이 필요하고,
스크롤은 글을 못 읽는 아이에게 보이지 않는 것과 같다.

### 7.2 명도 순환 버튼

앱바에 64dp 버튼 하나. 누를 때마다 밝게 → 기본 → 어둡게 → 밝게 로 돈다. 현재 명도를 버튼이
보여준다. 팔레트 8색의 명도가 함께 바뀐다. 유아 모드에서는 렌더링하지 않는다.

### 7.3 명도 24색을 어떻게 만드는가

상위 스펙 9장은 "8색 × 3명도 = 24색"이라고만 하고 밝은/어두운 값을 주지 않는다. **여기서
정한다.** 기본 8색은 상위 스펙의 hex 를 그대로 쓰고, 나머지 둘은 HSL 명도(L)를 옮겨 만든다.

| 단계 | 규칙 |
|---|---|
| 밝게 | `L' = L + (1 − L) × 0.45` |
| 기본 | 상위 스펙 9장의 hex 그대로 |
| 어둡게 | `L' = L × 0.62` |

색상(H)과 채도(S)는 건드리지 않는다. 곱셈으로 정의하는 것은 의도된 선택이다 — 고정 오프셋을
쓰면 이미 밝은 노랑(`#f1bd45`)이 흰색으로 날아가고 이미 어두운 갈색(`#795548`)이 검정으로
뭉개진다. 비율로 옮기면 여덟 색이 각자 제 자리에서 같은 정도로 움직인다.

**흰색(`#f5f5f5`)은 예외다.** 밝게 하면 배경과 구분되지 않고, 계획 2 최종 리뷰가 바로 그
대비 문제(1.06:1)를 잡았다. 흰색은 세 단계에서 각각 `#ffffff` · `#f5f5f5` · `#d0d0d0` 을
쓴다. 테두리 규칙(계획 2 의 `#757D75`)은 세 단계 모두에 그대로 적용한다.

구현 시 24색을 **미리 계산해 상수 표로 고정하고**, 그 표가 위 규칙과 맞는지를 테스트로
잠근다. 런타임에 HSL 변환을 돌리면 기기마다 반올림이 달라질 수 있다.

### 7.4 구체 수치

| 항목 | 값 | 근거 |
|---|---|---|
| 크레용 굵기 | 캔버스 좌표 24px | 1024 캔버스에서 손가락 자국만 한 굵기 |
| 붓 굵기 | 캔버스 좌표 48px | 크레용의 두 배, 넓게 쓸기용 |
| 지우개 굵기 | 캔버스 좌표 48px | 붓과 같게 — 지우려는 아이는 넓게 문지른다 |
| 스티커 기본 크기 | 캔버스 좌표 160px | 1024 의 약 1/6 |
| 스티커 크기 범위 | 80px ~ 320px | 두 손가락 제스처로 조절 |
| 스트로크 점 간격 | 4px 미만이면 버림 | 점이 촘촘해도 그림이 달라지지 않고 덮임 판정만 느려진다 |

이 값들은 **추정이다.** 계획 1 의 임계값이 그랬듯, 실제 기기에서 아이 손가락으로 그어 보기
전까지는 확정이 아니다. 실행 중 어긋나면 계획서가 아니라 이 표를 고칠 것.

## 8. 연령 분기

`settings.json` 에 `ageMode` 를 둔다. 기본값은 유아.

| | 유아 3~5세 | 아동 6~9세 |
|---|---|---|
| 도구 줄 | 숨김 (양동이 고정) | 다섯 개 |
| 팔레트 | 8색, 명도 전환 없음 | 8색 + 명도 전환 |
| 되돌리기 | 연속 한 번 | 연속 50번 |

엔진은 하나다. `AgeMode` 플래그가 UI 만 가른다(상위 스펙 9장). 유아 모드에서는 도구 줄과
명도 버튼이 아예 렌더링되지 않으므로 캔버스가 오히려 넓어진다.

## 9. 테스트 전략

계획 2 에서 비싸게 배운 것을 앞당겨 적용한다.

- **좁은 화면 + 인셋 테스트를 1번 태스크에 넣는다.** 계획 2 는 위젯 테스트가 전부
  800×600 · 인셋 0 에서 돌아서, 팔레트 두 색이 화면 밖으로 밀린 것을 **태스크 리뷰 열 번이
  놓쳤다.** 도구 줄 · 팔레트 · 명도 버튼 · 스티커 서랍이 전부 64dp 를 지키고 화면 안에 있는지를
  320×640 · 하단 인셋 34dp 에서 처음부터 본다.
- **브러시 마스킹을 실제 픽셀로 확인한다.** 칠할 수 없는 픽셀(선 위, 배경)에 브러시가 남지
  않는지를 렌더링 결과에서 읽는다. 계획 2 막바지에 `translate`/`scale` 을 바꿔치기해도 61개가
  전부 통과하는 것을 발견했다 — 시각적 계약은 픽셀로 확인하지 않으면 확인한 것이 아니다.
- **되돌리기 순서 테스트.** 채움 → 획 → 스티커를 한 뒤 세 번 되돌리면 역순으로 사라지는가.
  스택을 레이어별로 쪼개면 깨지는 바로 그 성질이다.
- **`BatchCommand` 테스트.** 지우개 한 손짓이 스티커 하나와 채움 셋을 건드렸을 때, 되돌리기
  **한 번**에 넷이 전부 돌아오는가.
- **자동 저장이 굽지 않는지.** 채움만 바꿨을 때 `brush.png` 가 다시 쓰이지 않는지를 호출
  횟수로 확인한다.
- 위젯 테스트는 계획 2 처럼 저장·타이머를 가짜로 주입한다. `fake_async` 아래에서 이미지
  디코딩이 끝나지 않는 것은 확인된 제약이다.
